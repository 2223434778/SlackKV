## 2. 下一轮先做的小修补：已知terminal请求停止无用新增写入

实现一个默认语义明确、可单独开关/记录的 terminal optional-store gate：对于已知 `end_after_request=true` 且当前支持的独立会话，停止本请求为未来续接发起的新 host store。这是工程优化，不单独包装为创新。

保留当前请求读取已有 KV、正常计算、已有传输完成与引用结算。**不能为了禁写而在 lookup/load 前调用 end、清空目标或释放现有前缀**；请求真正完成时再按现有生命周期结束。不要跳过观察/注册逻辑导致最终 end 丢失。已发出的传输照常结算，只有未发出的可选写入可省略。

有其他会话共享同一内容时，“该会话结束”不等于“这些块永远无用”；本轮先限定于已支持的独立路径，不引入共享全局驱逐。

针对性验证即可：
- terminal请求仍能从已有host恢复，与cold输出一致；
- 新代terminal请求没有新增D2H，但正常输出、结束和tombstone仍成立；
- 已在途旧批次结清，普通非terminal续接行为不变。

**归因边界：**本次224MiB在long_end之后发生，不在两会话E2E计时范围内。删除它直接改善全协议流量/诊断请求成本，不能声称按现有计时定义改善了已测会话E2E。不要删历史诊断请求后与旧全协议数字直接比较。

这个优化任何基线都能利用。后续若把减少terminal写入作为M1优势，应提供相同terminal信号下的简单Full禁写版本，或把terminal gate共同应用于比较方法并明确命名；保留原始native Full结果。不能将通用终止优化全部归因于动态公平分配。

也不要顺便实现“当前GPU有命中就不存host”：当前命中不保证下次仍驻留，那需要独立的保留价值证据。

## 4. 真正需要回答的问题：动态分配在多会话竞争中是否比Full有净收益

当前长8192+短1024的总需求只有9216tokens，host为8192；短会话退出后，唯一长会话恰好完全装入host。Full能恢复出与M1相同的long3覆盖，是合理结果。这个smoke适合证明生命周期和借用功能，不能充分检验高竞争下保护多个续接前缀的价值；也不能由它否定之前32B的容量压力结果。

下一次只准备**一个小型、事先冻结的多会话竞争筛选**，由执行侧自主选择具体长度和次数：
- 建议3–4个会话，至少两个较长且各有后续复用；有长短差异、一次加入和一次退出，续接输入正常增长且保留历史前缀。
- 多会话已知可复用前缀总量超过host；先按bytes/token和活跃需求解释资源预算，不根据跑出来的延迟反复调到Full失败。可使用透明合成输入，不要求生产trace。
- 固定到达/工具等待规则、生成工作量和请求身份；各方法同GPU/host池、compiled设置、terminal信号和warmup规则。并行请求仍遵守同session串行，避免当前不支持的fork。
- 优先比较M1、StaticFair和强Full，方法间公共小优化要一致或单列。新workload不能复用旧NoHost结果来宣称相对收益；如需这种结论再补本轮NoHost。
- 保留每会话E2E、resume TTFT、实际ready前缀深度、重算tokens、双向迁移和回收重写。先证明“分配/退出→物理前缀变化→后续恢复→少重算→总体时间”链条；不要只报一条最快请求或迁移总量。
- 先少量匹配筛选即可，不强制反序多种子。仅在发生具体异常时补必要对照，不能重复到得到正数。

无需同时扩大模型、并发、共享支持和策略数量。先沿用已跑通的小模型与native实现；如果数据显示其重算太便宜、机制收益被固定开销淹没，再提出一次已有32B环境的迁移验证及成本，不立即扩成大模型矩阵。

这一步的成功不要求预先保证某个百分比：若M1胜Fair且比Full保留更多有效前缀、存在可解释的整体净收益，保留动态路径；若Full同样好而M1额外迁移/回收，则缩小动态策略适用范围，考虑低压力自然退化为全存。不要通过强加预取来掩盖无收益。

## 5. 共享prefix与旧SlackKV机制的顺序

共享system prompt是后续实际可用性的重要缺口：当前任一共有块就可能让整代停止可选写入。先在固定输入上量化回退比例，并将“独立前缀机制验证”与“共享输入覆盖”明确分开。

本轮不把完整共享树重写作为跑上述独立路径筛选的前置条件；若实际目标输入普遍触发回退，下个实现增量应优先解决最小共享前缀引用/计费，而不是M3。共享块物理容量只能计一次，不可仅删除shared检查、保留单owner逻辑；一会话结束不能删掉其他会话仍依赖的祖先。实现复杂度过高时明确支持边界，不用盐消除共享来假装支持。

旧SlackKV的物理释放反馈、原生恢复、在途引用保护已经参与M1。GPU短租约/JIT promotion/PSA仍应等明确出现“有恢复等待且有安全可重叠窗口”的测量后再融合；当前串行smoke不是这类证据。无需为了看起来完整而立即开启M2/M3。
