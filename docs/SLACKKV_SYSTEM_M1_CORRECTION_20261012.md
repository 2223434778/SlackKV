## 2. 必修问题：已结束的 generation 在 collect 后重新被接纳

审查方用该提交的原始 `PrefixController` 独立运行下面序列：

```python
from slackkv.m1.controller import PrefixController

c = PrefixController(10)
path = (b"a", b"b")
c.observe("first", "s", 0, path)
c.end("s", 0)
c.finish("first")
c.collect(("s", 0))  # 由物理适配器确认该成员已无驻留块后调用
late = c.observe("late", "s", 0, path)
print(late.reason, late.ceiling, c.allowed(late))
# 92e65cb 的实测输出：None 2 2
```

原因：`latest` 仅记录最大 generation；`observe` 只拒绝更小的值。`collect` 删除 Member 后，结束标记消失，同代请求被当成新成员。这违反报告“结束后须增加 generation”的调用契约。当前证据是逻辑生命周期缺陷，不是已证实的 KV 内容损坏。

修正要求：

- 将终止状态的有效期与物理 Member 的回收分开。可以扩展现有 session tombstone，不要求为每代永久保存一条记录。
- 已显式结束的 generation 在物理回收前后都不能重新获得目标或 optional-store 资格；旧请求不能通过改变 request ID 绕过。
- 更高 generation 仍可正常加入；相同 native 身份有旧引用时，继续使用当前“等待旧引用结清、后续正常请求重建”的行为。
- 迟到的旧 end 事件不能结束新 generation；重复 end 应幂等。
- 逻辑拒绝不等于丢弃旧 DMA 完成：有效旧 store/load 完成仍必须结清引用，重复通知不得改变新槽位。
- 普通 request finish / tool idle 不等于 session end。保留当前明确的终止入口；不要顺便加入 TTL 或自动失活策略。
- 无在途任务的缓存 reset 不应意外恢复已结束 generation 的准入；如 reset 定义包含完整控制器新生命周期，应显式区分并记录，不能默认混用。
- 未见过的 session/generation 的 end 事件如何处理，由执行侧明确契约；不必为此新增网络事件服务或扩大本轮范围。

## 3. 最小必要回归

先让新回归在旧代码上暴露缺陷，再修复。覆盖以下行为即可，不要求扩展成大规模随机矩阵：

1. end → finish → collect → 同代迟到 observe：拒绝 optional store，不恢复成员份额；collect 前也拒绝。
2. 同 session 更高 generation 可加入；旧 end/observe 不改变新代目标。
3. 在真实 native manager 中走至少一次显式结束后的物理回收，再提交同代迟到请求，确认不会重新写入；保留普通推理/native 合法读取的回退语义。
4. 在途 store 或 load 跨越 end/new-generation：不能提前 free，完成后守恒，最终无遗留引用；优先扩展已有审计场景而非复制一套框架。
5. 普通请求完成后，同代串行续接仍合法；避免把所有 finish 都封死。

运行现有 M1 控制器测试与 native 审计，以及受修改影响的相关回归。原 64 项测试和 v1/v2 PASS 仍是历史证据；不要覆盖旧结果或宣称其已经覆盖上述缺陷。新增结果使用独立目录，例如 `results/system_m1_fix_20261012/`。

优先级：

### A. 真实内容与生命周期

先验证 M1 请求可完成，至少观察到实际 host store 和随后的非零 host restore；GPU 全命中不足以验证恢复路径。使用普通容量压力形成回收，不把强制清空 GPU 的机制诊断包装为自然端到端结果。

用小组有意义文本、确定的输出 token 数，在适当的 batch-invariant 配置下与独立冷 prefill 比较输出 token IDs；冷参考须核实无 local/external 命中。正确性配置单列，不混入普通 compiled 性能对照。

覆盖长短会话加入、一次显式退出、下一正常请求扩额，以及结束后同代迟到请求的安全回退。实际触发的在途保护、取消、引用结清要有事件证据；仅完成请求不能代替这些证据。未能在 GPU 触发的分支明确标记 CPU/native 已测、GPU 未覆盖，不靠无界加跑补齐。

最低验收：请求正常结束；已结束代不重新取得 optional-store 资格；恢复内容匹配；`ready + pending + free = capacity`；无保护块提前释放；已结束且引用结清的会话无遗留物理占用。活跃会话的合法缓存和 allocator 常驻池不算泄漏。

### B. 一个动态机制对照

A 通过且预算允许时，运行一个短长混合、成员加入与退出的固定脚本，优先 M1 对 StaticFair。模型、GPU/host 预算、输入、输出长度和到达/工具等待规则匹配；StaticFair 的固定配额规则须事先写明，不故意压低其份额，不给 M1 未来信息。

观察是否发生完整因果链：
短需求释放未用份额 / 成员退出 → 长会话目标增加 → 下一正常请求实际保存更多连续前缀 → 后续恢复多读取、少重算 → 是否改善会话完成时间。

同时报告缩额/重写代价、H2D/D2H、各会话 TTFT/E2E；若有后台请求，保留其完成时间和输出阶段代价。trace 配置两方法应可比，详细诊断日志不能悄悄只加在一种方法上。

Full / true NoHost 基线继续保留并准备好，按剩余额度补跑；未执行就写未执行。只跑 M1/StaticFair 能支持二者在这个场景的初步比较，不能声称胜过未跑基线。没有改善也可以结束本轮：说明动态机制是否生效、收益被什么成本抵消，不追着某个百分比调参。

## 5. 共享前缀与性能范围

当前跨会话共享导致整代停止 optional writes 的覆盖限制已知，本轮不要求实现完整共享计费。增加或复用一个“相同 system prefix + 不同会话后缀”的小型诊断，报告回退请求数与原因；不通过 session 盐消除共享后宣称支持真实共享 workload。可先用 CPU/native 验证这一覆盖行为，不为它额外扩大 GPU 矩阵。

若实际准备使用的输入几乎全部触发共享回退，就不能用其性能结果声称验证了动态分配；明确这一事实，提出最小兼容修补方案供下一步决定。独立前缀实验可继续作为受限机制验证。
