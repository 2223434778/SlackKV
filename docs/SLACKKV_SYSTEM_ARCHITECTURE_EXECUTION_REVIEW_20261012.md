# 新架构执行侧审查

审查 GitHub main `719d856`，读取架构、最新 AGENTS、32B报告与独立复核，并核查正在使用的 native CPU manager、LRU、BlockStatus及connector store/completion源码。本次只审查；没有M1实现、CPU生命周期新实验或GPU运行，不改写旧结果。连续GPU账本仍为4.1919880197h，旧4.5h例外不扩展。

**总体接纳。** M1围绕有限host的可复用前缀管理，比继续旧JIT调参更有实测依据。max-min、成熟offload和尾部回收可以组合，不因组件已有论文覆盖而否决。先做动态成员/非均匀长度的可运行能力，不必先重复旧大矩阵；新的性能声明仍需后续真实验证。M2/M3按需要增量加入，预取保持关闭。

下面是应明确的实现契约，不是推翻架构的理由。原文已提到多数风险，但概念接口尚不构成原生实现。

## 1. 回收与写入必须共用原生物理入口

实际 `CPUOffloadingManager.prepare_store()`在空间不足时调用`_policy.evict(n, protected)`；LRU只检查`ref_cnt == 0`和当前protected key集合，没有会话、配额或前缀父子语义。当前manager没有按指定尾块安全回收的公开接口。只调`max_offload_tokens`，或只在成员加入时做一次尾部回收，然后仍让普通LRU自由选victim，都不足以实现目标控制。

M1需要小范围原生扩展：选择合法victim并原子更新policy、free list和移除事件；所有受控新增store走同一入口。禁止控制器直接删私有字典，禁止用`reset_cache()`代替缩额。目标quota、实际连续深度和物理free必须分别记录。

## 2. 冻结计划不能等于无限期兑现额度

例：10块池，A旧请求计划10块，已写2块；B加入后目标变为A/B各5块。若只计当前在途写入、不约束A后续chunk，旧计划仍可能继续申请至10块，挤掉B新存的前缀。

建议冻结的是请求的身份/准入上限，而非保证其未来每块一定可写。每次原子store要复核实际净新增物理块、有效承诺及允许回收的victim；额度不足就拒绝可选store，模型继续执行。若选择预留整个旧计划未使用额度，也必须有明确释放条件和可见的延期回收账，而非隐藏长期占位。

ready物理块与pending-store物理块应互斥计数；load引用是已有ready块的保护状态，不再次加成CPU容量。未落到物理槽的有效承诺另计，不能靠目标quota总和证明安全。

## 3. native引用状态与迟到完成要精确处理

`BlockStatus.ref_cnt == -1`是未完成store，正数是读取引用，只有0才是引用条件下可回收候选；不能使用`<= 0`。实际completion由scheduler汇总所有TP worker的`pending_count`后才调用manager完成接口，单rank返回不等于块可释放。

若最深尾块仍受保护，不能跳过它删更浅块并继续声称前缀连续。可延期回收，或在明确验证整段安全后回收；不能为兑现新quota制造洞。

旧session/generation的完成通知不能增加新成员额度，但**仍必须结清旧native引用和物理状态**。区分物理生命周期结算与当前逻辑计划更新，不简单丢弃迟到通知。

## 4. 第一版支持范围要明确，共享降级也要计费

建议M1先限制到已验证的full-attention布局和原生LRU，并明确同一session的并行分支、重写/截断输入如何处理。session ID不能决定KV身份，也不能把其历史所有分支折成一个“当前长度”。

真实chat模板常包含共同前缀，“共享时降级”有可能经常发生，不能把仅互不共享的验证称为通用Agent支持。不强求M1立即完成共享公平计费，但fallback块必须计入同一物理池，并把其驱逐结果反馈给受控状态。单个未知请求直接切Full、却不计其占用，会破坏其他成员的额度；初版可选择停止该请求的可选写入或一致地退回保守策略。不得用session盐偷偷消除原有共享后声称配置完全匹配。

原生`next_stored_block_idx`会随已发起store推进。尾部回收或目标扩张后不能仅改计数就假定旧请求自动补回；M1可保守地让恢复深度在下一次正常请求中增长，不急于重置游标或主动重算填池。

## 5. 公平与性能承诺保持克制

max-min是缓存资源分配公平，不是会话延迟或GPU执行公平；短会话借出空余容量是能力测试，不能自动宣称E2E加速。保留Full、NoHost和StaticFair对照，分别检验动态成员/非均匀需求带来的额外价值。

旧32B正结果仍只有单组三方法；本架构不会扩大其统计有效性。旧第三BG输出阶段平均间隔代价需保留，后续测量客户端流式到达明细，区分SSE分包与真实逐token间隔。

M1的max-min在已知需求总量不超过容量时本就退化为完整保存；M2的额外压力模式与滞回先证明有必要，避免为阶段编号增加重复状态。M3仅在测得恢复关键路径机会后接入。

## 决定

不建议推翻或大改Astra路线。先把M1的原子store/reclaim入口、旧计划承诺结算和prefix身份覆盖范围落实，再扩M2/M3。当前用户任务是架构审查，本次没有把这些建议冒充已实现或已测试功能；下一次M1实施按最新AGENTS推进代码与CPU/native验证，再依据具体GPU smoke范围申请新的预算。
