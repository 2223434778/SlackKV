## 1. 用户目标与当前指令

用户明确将目标从论文研究转为 infra 实习项目：自己搭建、运行、理解一个完整系统。项目继续，但不再以算法新颖性、打败所有基线或完成 M1/M2/M3 为验收条件。本交接取代旧研究方向限制和“暂停所有开发”的建议；旧研究证据、资源账本与安全契约继续保留。

执行 Codex 请直接开始实现，短暂盘点后交付代码，不再只提交方案或机会分析。可自主决定目录、CLI、轻量依赖和实现细节；按下述 E1→E2→E3 分阶段提交，每个阶段明确实际验证范围。范围内无需逐项等架构审批。遇到一个阻塞先推进不依赖它的部分；不虚报 GPU 验证完成。

项目定位：

> 基于 vLLM 原生 CPU offload 的多会话 KV 缓存管理与观测系统，通过容量受限的前缀准入减少部分负载中的缓存抖动和重复 Prefill，提供可复现部署、多轮客户端、生命周期处理与性能对比。

使用已验证技术栈，先做单机单卡。双卡/32B 是已有实验资产及后续可选配置，不是首次启动的前提。

## 2. 可复用资产及实现边界

优先检查并复用：
- `slackkv/m1/spec.py`、`native.py`、`controller.py`：原生接口、终止语义、引用结算、共享根和回收。仅提取工程主线确实需要的部分，不把整个动态控制器强塞进 StaticFair。
- `experiments/system_m1/smoke.py`、`contention.py`、`install.py`、`native_audit.py`：环境接入、服务启动、指标采集和已有验证。这里存在旧实验专用参数和预算检查；提取通用逻辑，不改写旧 runner 以绕过限制。
- `experiments/host_prefix/` 及 `experiments/large_model/`：固定前缀准入、对比和归档工具。
- 旧实验数据继续留在原目录，新工程交付单独归档。

三种明确模式：
1. NoHost：不启用 offload connector。
2. Full：原生全量写入/LRU，固定且公开 host 预算。
3. StaticFair：明确配置的最大会话槽位及每槽位固定连续前缀额度，同一 host 预算；它是工程演示主线。
动态 M1 为 opt-in experimental，继续保留负结果；不再调参或开发 M2/M3。

StaticFair 的槽位、空闲额度、短会话未用额度和超过上限的行为必须明确。首版允许保守固定额度、有限队列/明确拒绝，不暗中变成动态借用算法。共享根只在已验证边界内计一次；不支持的布局明确回退或拒绝。初版也可以使用独立会话身份隔离，清楚说明该配置不提供跨会话共享，并保留已有共享测试。

核心执行使用 vLLM 原生 scheduler、KV allocator、connector 和复制通路。应用侧负责协议、会话及准入参数。不得宣称自研推理引擎、CUDA kernel 或完整生产级缓存系统。

## 3. E1：先交付最小可运行纵向流程

目标：完成环境检查→启动服务→多个真实多轮会话→结束/退出→生成机器可读报告。

### 环境与统一入口

- 增加 README、最小打包/依赖声明和集中配置，提供 doctor、serve、demo、report 等等价命令；具体命令名自主确定。
- 固定并验证现有已成功的 Python/PyTorch/CUDA/vLLM 版本及必要源码 commit/patch。区分“已实测配置”和“可能兼容”；不要默认升级到最新。
- 如果依赖 fork、私有补丁、实验路径或 conda 绝对路径，将必要安装步骤与补丁来源显式纳入复现；清理机器专属路径。安装检查幂等，版本不匹配有可理解的报错。
- 模型路径、设备、端口、host/GPU KV 预算、上下文上限、会话数可配置。先使用已下载且验证过的小模型，默认仅绑定本机。
- doctor 检查版本、模型、可用资源、端口与 adapter 能力；不得为“检查”自动下载大模型或占用另一张 GPU。
- 启动过程有 ready 探测、超时、日志、退出码和 owned process 清理；只操作自己启动的进程。记录配置和源码版本。
- 提供无 GPU 的配置/协议自检入口，并明确它不能替代真实 KV 验证。

### 真实多轮客户端与最薄服务层

- 优先直接使用现有 vLLM HTTP 接口；只有会话状态/控制确有需要时增加轻量服务层，避免先做完整网关。
- 演示至少两个独立会话、每个至少三轮。保存真实 user/assistant 历史，下一轮包含上一轮真实生成结果；遵守 chat template 和 EOS，不用随机 token 或固定输出占位冒充真实聊天。
- 提供一个可重复、无外部付费 API 的本地工具步骤，例如查本地 JSON 文档；客户端驱动工具流程即可。若不是模型自主选择工具，文档如实描述。
- 明确 session_id、generation、request_id 的关系；区分请求结束、工具等待、会话结束。
- 首版同一会话只允许一个在途请求，明确拒绝或排队并发续接；不同会话可独立运行。保留取消/失败时的一致历史，不能把半个响应写成完整已提交轮次。
- 对已知最后一轮使用现有 terminal gate。若用户在最后一轮之后发起独立 close，核查当前 native 接口是否支持安全通知：需要新增时使用有序控制通路及确认，禁止无锁跨进程改 manager。首版可明确标为“逻辑关闭；物理缓存随 native LRU/在途结算释放”，不能声称关闭即物理回收，也不能发送假推理请求冒充控制。
- 服务重启后内存会话丢失可作为首版限制；如提供客户端历史重建，应重新建立身份并正常 prefill，不能把旧 KV 状态当仍有效。

### E1 验收

实际小模型完成一条启动/会话/报告/停止流程，StaticFair 主线可运行，三种模式的配置入口已实现并记录哪些真实测过。输出命令、示例会话、逐请求时戳、配置、日志和 summary；停止后进程与资源可确认清理。

真实会话 demo 不强求出现 host 命中或胜过 Full。另复用已有小型受压恢复检查，证明真实 D2H/H2D 与内容正确性；热 GPU demo 无 host 恢复时不能把 GPU 命中归因于 offload。两者分开呈现。

先提交这个能用的 E1，再继续扩展，不要先完成所有文档/监控平台。

## 4. E2：可靠性、可观测性和小型 benchmark

### 可靠性

在既有生命周期测试基础上补实际新边界的测试：
- 超过会话/上下文/队列限制；参数非法；结束后续接。
- 请求中途断开、超时或失败，历史提交和 pending 引用处理。
- 重复 close、同会话并发、generation 变化。
- load/store 在途不能提前释放，失败和迟到完成最终可结算。
- 服务启动失败和正常退出都不遗留 owned process。
CPU 单元测试与真实 native/GPU 集成测试分开；CI 无 GPU 时明确 skip 原因。已有未覆盖路径如实列出，不为了完整标签大量新增无意义测试。

### 指标与报告

复用现有 Prometheus 和日志即可，不要求 Grafana 或网页：
- 请求 TTFT、完整响应时延；会话 E2E 明确起止及工具等待。
- 首 token 到结束平均间隔可展示，但没有逐 token 时间就不能称为 TPOT 分布。
- GPU 命中、host 恢复、实际重算 tokens。
- D2H/H2D 字节、host 配置容量与实际占用（仅接口确能观测时）、在途状态。
- 超时/失败数、请求/会话数量、整体运行时长、工作量和资源。
- 缺失指标标 UNKNOWN，不补零；并发期间全局计数差不能假称单请求归因；高基数 session_id 不作为默认 Prometheus label。

生成 JSON/CSV 和可读 Markdown 报告即可。详细调试追踪可开关，性能模式下各方法追踪开销一致。

### 小型对比

建立三个固定用途的场景：GPU 热复用、host 足够、host 受限。资源与工作量预先记录，按实际需要执行小规模 smoke，不开展容量/种子大矩阵。

公平对比使用冻结请求/token 输入、相同输出工作量和相同资源；真实自由生成的 demo 因策略输出可能不同，不能直接用于严格吞吐排名。需要加入明确的少量重叠请求验证跨会话并发，不能把交替串行称为并发服务。

NoHost/Full/StaticFair 均保留，允许 StaticFair 在某些场景无收益或更慢；验收看工作正常、指标可信、取舍可解释，没有“必须快 X%”门槛。已有32B历史结果可以引用，不必为面试项目重跑，并标注合成负载和版本。
